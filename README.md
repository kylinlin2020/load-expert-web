# 装柜专家 LoadExpert（Web 版）

基于 Vue3 + TypeScript 全栈实现的现代装柜计算软件：**货物管理、柜型管理、装柜计算、3D 结果展示、报表导出、历史方案、数据备份**。

## 技术栈

| 层 | 技术 |
|---|---|
| 前端 | Vue 3 + Vite + TypeScript + Element Plus + Three.js（3D 可视化） |
| 后端 | Fastify + node:sqlite（Node 内置 SQLite，无需原生编译） |
| 算法引擎 | 自研三维装柜算法（`src/algorithm`）：多起点候选块 + 空间分割 + 堆码/承托约束 + 单纯形配比 |

## 两套构建产物

界面完全相同，**区别只在数据放哪儿、算法在哪儿跑**。页面「应用版本」页右上角会显式标注当前是哪一套。

| | 服务端版 | 纯静态版 |
|---|---|---|
| 构建命令 | `npm run build:web` | `npm run build:web:static` |
| 数据 | 后端 SQLite `data/load-expert.db` | 浏览器 IndexedDB（库名 `load-expert`） |
| 算法在哪跑 | Node 服务端 | **浏览器内** |
| 路由 | history（URL 干净） | hash（`/#/calculate`） |
| 运行要求 | 需要 `npm run server` | **纯静态文件，扔哪都能跑** |
| 托管成本 | 需一台服务器 | **零**（GitHub Pages / 对象存储 / 任何能发文件的地方） |

**两套跑的是同一份算法代码**（`src/algorithm` 零 Node 依赖，直接编进浏览器包），
装载率不会因为换了版本而变。**但两边的数据互相独立、不会同步** ——
静态版录入的货物不会出现在服务端版，反之亦然。

> ⚠️ **静态版的数据只存在于用户自己的浏览器里，没有服务器副本。**
> 换浏览器、换电脑、换域名都看不到；清除浏览器数据 / 站点数据 / 用无痕窗口，
> 录入的货物、柜型、方案**全部丢失且无法恢复**。只应在一个固定浏览器里使用。

### 部署纯静态版到 GitHub Pages

```bash
npm run build:web:static
```

产物在 `dist/web/`（含 `.nojekyll`），把它推到仓库的 `gh-pages` 分支或 `/docs` 目录即可。

之所以能做到「同一份产物扔哪都能跑」，靠两点：

- **hash 路由**（`createWebHashHistory`）：GitHub Pages 与绝大多数对象存储
  **不做 SPA 的 history fallback**，请求 `/仓库名/装柜计算` 会直接 404。
  路由放进 `#` 之后，服务器只需回一个 `index.html`。
- **相对资源路径**（`base: './'`）：index.html 里所有资源引用都相对于当前 HTML 所在目录，
  所以项目站 `/仓库名/`、用户站 `/用户名/`、任意子目录都不用重新构建。

> 直接双击本地 `index.html`（`file://`）**不行** —— 浏览器禁止 `file://` 使用 IndexedDB。
> 要在本地试，用 `npm run preview:static` 起个本地服务器。

### 构建产物自检

`build:web:static` 末尾会自动跑 `scripts/check-static-bundle.mjs`，检查三件事：

1. 产物里**没有** Node / 服务端代码（`node:sqlite`、`fastify`、`DatabaseSync`…）
2. 产物里**有**算法引擎指纹 —— 防 Vite 把静态分支误判成死代码、连算法一起摇掉。
   那种故障页面照样打得开、柜型列表照样有数据（种子照写），只在点「开始计算」时才炸
3. 资源引用是相对路径，且 `indexedDB` 在包里

> 标记本身也可能过期，所以每项都会**回查源码**：标记若已从算法里消失，
> 报「标记过期」而不是误报「算法被摇掉」。两类问题必须分清，否则这个检查很快会被忽略。
> 重新挑标记用 `node scripts/find-algo-markers.mjs`。

## 启动步骤

### 1. 启动后端 API（默认端口 3000）

```bash
npm run server
```

首次启动会自动创建 `data/load-expert.db` 并写入 20GP / 40GP / 40HQ 三个标准柜型种子数据。

### 2. 启动前端开发服务器（默认端口 5173）

```bash
npm run dev
```

浏览器访问 **http://localhost:5173**（若 5173 端口被占用，Vite 会自动顺延使用 5174 等端口，以启动日志显示的实际地址为准）

前端默认走**同源相对路径** `/api`，由 Vite 开发服务器代理转发到 `http://127.0.0.1:3000`（避免浏览器把 `localhost` 解析为 `::1` 而后端仅监听 IPv4 导致的连接失败）。如需直连后端完整地址，可在项目根目录创建 `.env` 文件：

```
VITE_API_BASE=http://127.0.0.1:3000
```

### 3. 生产构建（可选）

```bash
npm run build               # 生成版本文件 + 编译后端（tsc，输出 dist/）
npm run build:web           # 服务端版前端（vite，输出 dist/web/）
npm run build:web:static    # 纯静态版前端 + 产物自检
npm run preview             # 本地预览服务端版产物
npm run preview:static      # 本地预览纯静态版产物（IndexedDB 需要真实 origin，不能用 file://）
```

> **构建时提示 `memory allocation of N bytes failed`？**
> 这是内存争用，不是代码问题 —— 表现为 `rendering chunks` 阶段失败、退出码 127。
> 常见于同时开了 Photoshop 等占内存的大程序时（Vite 用的 Rolldown 是 Rust 写的，
> 默认的 V8 堆预留会把系统内存挤光，导致原生分配失败）。
> 先关掉占内存的程序，或限制 V8 堆再构建：
>
> ```bash
> # PowerShell / CMD
> set NODE_OPTIONS=--max-old-space-size=1536 && npm run build:web:static
> ```
>
> GitHub Actions 上一般不会遇到（runner 空闲内存更多）。

### 实测案例（算法反馈）

最有价值的反馈不是"界面点不动"，而是**同样的柜型 + 货物，算法算出 966 箱、现场实际只装到 900 箱**。这类数据能直接改进算法。

- 录入：装柜计算页算完后点「记录为实测案例」（紧挨「保存方案」—— 两个动作服务同一场景）
- 补录：现场装完后到「实测案例」页填实际箱数/柜数
- **柜型存快照而非 id 引用** —— 用户事后调整柜型尺寸，这条案例仍反映"当时算的时候用的柜子"
- **`computed`（算法输出）与 `actual`（现场实测）分开存** —— 前者由程序填且**不可修改**，所以补录实测不会篡改算法输出
- 偏差自动计算，不让用户手填（手填的偏差一定会和实际对不上）
- 列表**按偏差排序**而非时间：偏差大的排最前，吻合的垫底

> 排序与总览里刻意区分「算法高估」与「算法保守」——
> **高估是最需要警惕的方向**：程序给的方案在现场装不下，发出去是要出事的。

### 意见反馈


| 采集 | 说明 |
|---|---|
| Vue 渲染/事件错误 | `app.config.errorHandler` |
| 未处理的 Promise 拒绝 | `unhandledrejection` —— **少这一类最亏**，视图里大量 `await api.xxx()`，漏了 catch 界面毫无反应 |
| 脚本与资源加载错误 | `window.addEventListener('error')` |
| 路由跳转轨迹 | 用于还原"出错前做了什么" |

三条硬约束：

- **不落盘。** 只存内存环形缓冲（最近 50 条），关页面即消失。静态版的数据本来就在浏览器里，不该再往磁盘堆没人会看的东西。
- **不采集业务数据。** 诊断里**一个货物名/尺寸/柜型字段都没有**，只有版本、构建模式、浏览器、数据**条数**、错误堆栈。
- **不接第三方表单服务。** 避免把诊断信息发给第三方。

提交方式两条都给（无后端环境的现实约束）：

| 方式 | 适用 |
|---|---|
| **复制诊断信息** / 下载诊断包 `.json` | 最可靠 —— 不需要账号、离线可用。诊断包是无损的，含完整堆栈 |
| **提交 GitHub Issue**（预填标题与正文） | 有 GitHub 账号时更方便，结构化可追踪 |


### 数据备份与恢复

菜单里的「数据备份」。**两套构建用的是同一种文件格式**，因此可以互相搬数据。

| | 导出 | 导入 |
|---|---|---|
| 界面 | 「数据备份」页 → 导出为 JSON 文件（文件名含版本号与时间戳） | 选择 `.json` 文件 → 选模式 → 导入 |
| 服务端版 API | `GET /api/backup/export?includePlans=0` 可排除方案 | `POST /api/backup/import?mode=merge\|replace` |

**两种导入模式**

| 模式 | 行为 | 适用 |
|---|---|---|
| **覆盖恢复**（默认） | 清空现有全部数据，再按文件内容写入 | "恢复到备份时的状态"、从另一套版本搬数据 |
| **合并导入** | 按 id 对齐：文件里有的覆盖或新增，**文件里没有的现有记录一律保留** | 往已有数据里补充内容 |

覆盖恢复会**在清空前自动下载一份当前数据**作为退路，再要求确认 ——
让用户在点之前不用做任何事就能拿到当前状态的备份，选错文件也有退路。

> 校验刻意**严格**：任何一条记录不合法就整体拒绝，并指出是哪一条的哪个字段，
> 不做"跳过坏记录"。恢复操作里静默丢记录是最坏的失败方式 —— 用户以为全部恢复了，
> 几天后才发现少了几条柜型。

> **导入会补齐老记录缺失的字段**（如 `deformFactor` / `allowDirections`），这是
> **单向归一化**，不是丢数据：算法判定是 `allowDirections?.[o] === false`，
> 缺省与 `[true×6]` 等价。归一化之后往返即幂等，由测试锁定。

> **id 原样保留**：存下来的 `PackResult` 里到处是 `boxId` 引用
> （`placements[].boxId` 等），`Plan.containerId` 指向柜型。重新分配 id 而漏改引用，
> 界面不会报错，只会默默显示错货名 —— 所以导入严格按文件里的 id 写回，
> 由「导出 → 导入 → 再导出」的幂等性测试盯着。


### 导出

| 导出 | 格式 | 说明 |
|---|---|---|
| 装柜报表 | **PDF** | 基本信息 / 汇总指标 / 装入清单（申请 vs 装入，数量留空显示「不限」）/ **3D 示意图** / 分层明细 / 未装清单 |
| 装柜步骤单 | **PDF** | 逐条摆放顺序 + 完整坐标区间 + 累计装载率 + 签字栏 |
| 逐箱坐标 | CSV | 每行一箱 |
| 装柜步骤 | CSV | 同步骤单的 CSV 版 |
| 3D 视图 | PNG | 3D 面板内导出 |

**PDF 采用「打印 → 另存为 PDF」**：PDF 规范无内置中文字体，jsPDF/pdfmake 要显示中文
必须内嵌 CJK 字体（微软雅黑约 19MB），为一个打印功能付出这种体积不划算；
浏览器打印到 PDF 是**真矢量文字**、中文天然正确、**表格跨页自动重复表头、行不截断**，
且零新增依赖。代价是需在打印对话框选「另存为 PDF」而非点一下直接下载。

> 打印页与计算页**共用同一套行数据派生逻辑**（`src/web/lib/packRows.ts`），
> 避免出现"打印的步骤单和页面看到的对不上"。

**3D 示意图**：报表页里可以拖拽旋转挑角度，点「生成 3D 示意图」把它定格成图片；
打印时印的是这张定格图（不是 WebGL canvas —— 各浏览器对"打印时取 canvas"的时序处理
不一致，会印出空白帧）。屏幕上同时显示这张图的缩略预览，便于确认要印的内容不是空白。

## 货物字段（编辑弹窗分 4 页签）

| 页签 | 字段 | 算法是否使用 |
|---|---|---|
| 基本信息 | 名称、描述、SKU、批次、颜色、分组、单价、单位、每箱件数 | 名称/数量用于算法；**颜色**用于 3D 与图例；其余存档 |
| 尺寸与重量 | 长 L / 宽 W / 高 H、尺寸单位、毛重、净重、重量单位 | 长宽高、毛重使用；净重/单位存档（算法内部统一 mm / kg） |
| 型变 | 型变系数 `deformFactor`、型变公差 `deformTolerance` | **系数已生效**：实际占位尺寸 = 名义尺寸 × 系数；公差存档 |
| 摆放限制 | 堆码级别、底部承托比例、六向设置 | 堆码级别 / 承托比例 / 六向「允许摆放」「承托级别」已生效；六向「最大堆放数」「可承重」存档 |

**六向设置**是一个 6 行表格（`dir0 长×宽×高` … `dir5 宽×高×长`），每行 4 列：

| 列 | 字段名 | 语义 | 算法 |
|---|---|---|---|
| 允许摆放 | `A~F_ALLOW` | 该方向禁止摆放 | ✅ 未勾选的方向直接排除 |
| 承托级别 | `A~F_SUPPORT_STACK_CLASS` | 0 表示该向不允许；非 0 值是它作为下层时可承托的上限 | ✅ 参与方向准入与堆码约束 |
| 最大堆放数 | `MAX_PLACE_DEEP/HORZ/VERT` | 该向最多堆几件 | ❌ 存档 |
| 可承重 | `A~F_BOTTOM/TOP/HEAD/TAIL` | 该向底面能否承托上层 | ❌ 存档 |

**型变系数**说明：软包装/可压缩货物受压后实际占位小于名义尺寸时，把系数设为 < 1（如 0.85 表示三轴各压缩 15%），算法会按压缩后的尺寸生成候选块、放置坐标与 3D 渲染，**装载率分母口径与之一致**（不会算出 >100%）。

## 柜型字段

内尺寸、载重、尺寸单位、重量单位参与计算；**角件尺寸、门尺寸、空柜自重、成本、计量单位目前仅作数据存档** —— 装柜计算按内尺寸与载重进行，角件冲突检测尚未实现。

### 装载率对标（现场实测场景）

40HQ 11900×2340×2680，水泵2 480×380×380 ×630 + 水泵3 515×380×425 ×336：

## 装柜步骤（现场作业单）

装柜步骤的**排序规则与列结构由本项目自拟**，按装柜作业通行做法实现 ——
没有权威规范可依，因此**与其他系统的步骤单不一定可互相套用**，
对接前请先核对列含义与排序顺序。

**一步 = 一个聚合放置块**（`result.placements` 的一条），即「把这块推进去」这一个动作。
逐件坐标带 `placementIndex`，故能把每个箱子精确归到所属步骤。

**排序规则（物理可执行）**

1. **z 底面升序** —— 必须自下而上，否则会出现"空中楼阁"（先装的箱子悬空）。
   由于任何 z=k 的箱子必然坐在某个 zMin<k 的箱子上，按 zMin 升序即保证**承托先于被承托**。
2. 同层按**距柜门由远及近**推进：先装柜内深处、最后装靠近门口，卸货时靠门的先取。

> ⚠️ **柜门位置未在容器模型中记录**（只有 `doorDims` 门尺寸，没有门在哪一端），
> 故做成界面上的显式切换「柜门在深处端 / 柜门在本端」，不把约定偷偷写死。

**每步显示**：步号、姿态（平放/侧放/立放）、货物名、单箱占位尺寸、件数、占位区域（X / Z 区间）、
累计件数与累计装载率（"装到这里就够了"）。点击某步可在 3D 中**高亮该步骤装的箱子**（按实例着色，
同一种货物分布在多个步骤时也能区分）。可导出 CSV 作业单（含柜型/内尺寸/装柜顺序/装载率表头）。

## 柜型尺寸基准

首次启动会写入 3 个**默认参考柜型**（ISO 668 数值）：

| 柜型 | 内长 × 内宽 × 内高 | 载重 |
|---|---|---|
| 20GP | 5800 × 2340 × 2380 | 21770 |
| 40GP | 11900 × 2340 × 2380 | 26800 |
| 40HQ | 11900 × 2340 × 2680 | 26800 |

> ⚠️ **这些只是默认值，程序不会自动校正你的柜型数据。**
> 上表是**实测值**（而非 ISO 668 名义值，两者容积差约 2~3%，用名义值会让装载率系统性偏低），
> 但同一型号的集装箱实物仍有差异。种子只在**首次运行**（柜型表为空）时写入，
> 改了也不会影响已有数据库里的柜型。**请在「柜型管理」里按自己手上的设备核对。**
