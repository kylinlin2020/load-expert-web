# 装柜专家 LoadExpert（Web 版）

基于 Vue3 + TypeScript 全栈重构的现代装柜计算软件，功能对齐原 Windows 版 LoadExpert：**货物管理、柜型管理、装柜计算、3D 结果展示、历史方案**。

## 技术栈

| 层 | 技术 |
|---|---|
| 前端 | Vue 3 + Vite + TypeScript + Element Plus + Three.js（3D 可视化） |
| 后端 | Fastify + node:sqlite（Node 内置 SQLite，无需原生编译） |
| 算法引擎 | 自研三维装柜算法（src/algorithm），对齐原软件逆向分析结果 |

## 目录结构

```
load-expert-web/
├── src/
│   ├── algorithm/       # 装柜算法引擎（候选块、空间分割、堆码/承托约束、LP 配比）
│   ├── types/           # 核心领域类型（Box / Container / PackResult）
│   ├── db/              # SQLite 数据层（boxes / containers / plans）
│   ├── server/          # Fastify REST API
│   └── web/             # 前端（Vue3）
│       ├── main.ts      # 入口
│       ├── router/      # 路由
│       ├── App.vue      # 布局（侧边导航 + 内容区）
│       ├── api/         # fetch 客户端（baseURL 可配）
│       ├── views/       # 货物管理 / 柜型管理 / 装柜计算 / 方案列表
│       └── components/  # Packing3D.vue（Three.js 3D 可视化）
├── vite.config.ts       # 前端构建配置
├── index.html           # 前端入口页
└── data/                # SQLite 数据库文件（首次启动自动生成）
```

## 环境要求

- Node.js ≥ 20.19（推荐 22+，需内置 `node:sqlite` 模块）
- npm ≥ 10

## 安装依赖

```bash
npm install
```

## 启动步骤

### 1. 启动后端 API（默认端口 3000）

```bash
npm run server
```

首次启动会自动创建 `data/load-expert.db` 并写入 20GP / 40GP / 40HQ 三个标准柜型种子数据。

### 2. 启动前端开发服务器（默认端口 5173）

```bash
npm run dev
```

浏览器访问 **http://localhost:5173**（若 5173 端口被占用，Vite 会自动顺延使用 5174 等端口，以启动日志显示的实际地址为准）

前端默认走**同源相对路径** `/api`，由 Vite 开发服务器代理转发到 `http://127.0.0.1:3000`（避免浏览器把 `localhost` 解析为 `::1` 而后端仅监听 IPv4 导致的连接失败）。如需直连后端完整地址，可在项目根目录创建 `.env` 文件：

```
VITE_API_BASE=http://127.0.0.1:3000
```

### 3. 生产构建（可选）

```bash
npm run build        # 编译后端（tsc，输出 dist/）
npm run build:web    # 构建前端（vite，输出 dist/web/）
npm run preview      # 本地预览前端构建产物
```

### 导出

| 导出 | 格式 | 说明 |
|---|---|---|
| 装柜报表 | **PDF** | 基本信息 / 汇总指标 / 装入清单（申请 vs 装入，数量留空显示「不限」）/ **3D 示意图** / 分层明细 / 未装清单 |
| 装柜步骤单 | **PDF** | 逐条摆放顺序 + 完整坐标区间 + 累计装载率 + 签字栏 |
| 逐箱坐标 | CSV | 每行一箱 |
| 装柜步骤 | CSV | 同步骤单的 CSV 版 |
| 3D 视图 | PNG | 3D 面板内导出 |

**PDF 采用「打印 → 另存为 PDF」**：PDF 规范无内置中文字体，jsPDF/pdfmake 要显示中文
必须内嵌 CJK 字体（微软雅黑约 19MB），为一个打印功能付出这种体积不划算；
浏览器打印到 PDF 是**真矢量文字**、中文天然正确、**表格跨页自动重复表头、行不截断**，
且零新增依赖。代价是需在打印对话框选「另存为 PDF」而非点一下直接下载。

> 打印页与计算页**共用同一套行数据派生逻辑**（`src/web/lib/packRows.ts`），
> 避免出现"打印的步骤单和页面看到的对不上"。

**3D 示意图**：报表页里可以拖拽旋转挑角度，点「生成 3D 示意图」把它定格成图片；
打印时印的是这张定格图（不是 WebGL canvas —— 各浏览器对"打印时取 canvas"的时序处理
不一致，会印出空白帧）。屏幕上同时显示这张图的缩略预览，便于确认要印的内容不是空白。

## 货物字段（编辑弹窗分 4 页签）

| 页签 | 字段 | 算法是否使用 |
|---|---|---|
| 基本信息 | 名称、描述、SKU、批次、颜色、分组、单价、单位、每箱件数 | 名称/数量用于算法；**颜色**用于 3D 与图例；其余存档 |
| 尺寸与重量 | 长 L / 宽 W / 高 H、尺寸单位、毛重、净重、重量单位 | 长宽高、毛重使用；净重/单位存档（算法内部统一 mm / kg） |
| 型变 | 型变系数 `deformFactor`、型变公差 `deformTolerance` | **系数已生效**：实际占位尺寸 = 名义尺寸 × 系数；公差存档 |
| 摆放限制 | 堆码级别、底部承托比例、六向设置 | 堆码级别 / 承托比例 / 六向「允许摆放」「承托级别」已生效；六向「最大堆放数」「可承重」存档 |

**六向设置**是一个 6 行表格（`dir0 长×宽×高` … `dir5 宽×高×长`），每行 4 列：

| 列 | 原软件字段 | 语义 | 算法 |
|---|---|---|---|
| 允许摆放 | `A~F_ALLOW` | 该方向禁止摆放 | ✅ 未勾选的方向直接排除 |
| 承托级别 | `A~F_SUPPORT_STACK_CLASS` | 0 表示该向不允许；非 0 值是它作为下层时可承托的上限 | ✅ 参与方向准入与堆码约束 |
| 最大堆放数 | `MAX_PLACE_DEEP/HORZ/VERT` | 该向最多堆几件 | ❌ 存档 |
| 可承重 | `A~F_BOTTOM/TOP/HEAD/TAIL` | 该向底面能否承托上层 | ❌ 存档 |

**型变系数**说明：软包装/可压缩货物受压后实际占位小于名义尺寸时，把系数设为 < 1（如 0.85 表示三轴各压缩 15%），算法会按压缩后的尺寸生成候选块、放置坐标与 3D 渲染，**装载率分母口径与之一致**（不会算出 >100%）。

| 字段 | 默认 | 说明 |

## 装柜步骤（现场作业单）

原软件有「装柜步骤」输出（出现在方案打印中），逆向**未还原其排序规则与列结构**。
本项目的实现按装柜作业通行做法自拟，语义与原软件**不保证一致**。

**一步 = 一个聚合放置块**（`result.placements` 的一条），即「把这块推进去」这一个动作。
逐件坐标带 `placementIndex`，故能把每个箱子精确归到所属步骤。

**排序规则（物理可执行）**

1. **z 底面升序** —— 必须自下而上，否则会出现"空中楼阁"（先装的箱子悬空）。
   由于任何 z=k 的箱子必然坐在某个 zMin<k 的箱子上，按 zMin 升序即保证**承托先于被承托**。
2. 同层按**距柜门由远及近**推进：先装柜内深处、最后装靠近门口，卸货时靠门的先取。

> ⚠️ **柜门位置未在容器模型中记录**（只有 `doorDims` 门尺寸，没有门在哪一端），
> 故做成界面上的显式切换「柜门在深处端 / 柜门在本端」，不把约定偷偷写死。

**每步显示**：步号、姿态（平放/侧放/立放）、货物名、单箱占位尺寸、件数、占位区域（X / Z 区间）、
累计件数与累计装载率（"装到这里就够了"）。点击某步可在 3D 中**高亮该步骤装的箱子**（按实例着色，
同一种货物分布在多个步骤时也能区分）。可导出 CSV 作业单（含柜型/内尺寸/装柜顺序/装载率表头）。

> 步骤粒度 = 聚合放置块。若单步内跨越很大的空间跨度，现场可再按 x/y 子区域二次拆分（当前未做）。

## 计算策略（0~5）

6 个策略按**填充几何 + 姿态档**组合区分，会产出**不同的装柜结果**（装载率 84%~99%）：

| 策略 | 名称 | 姿态偏好（首选档） | 几何特征 |
|---|---|---|---|
| 0 | 单方向条块 | 最扁（heightRank0） | 只沿最长轴铺一条线，细长条块，为其它货物留出最大空间 |
| 1 | 单层薄片 | 最扁（heightRank0） | 横向铺满一个面、竖直只放一层，主动为上方保留空腔 |
| 2 | 逐层残层 | 次扁（heightRank1） | 每次放一层但允许末层不足整行，数量不整除时能多装 |
| 3 | 满舱主块（基准） | 最高（heightRank2） | 三轴尽可能堆满，**并按需求量拟合层网格**（找 a·b·c = 剩余量的整块，让几何残余自然留给其它货物），作为对照基准 |
| 4 | 承托分级分层 | 次扁（heightRank1） | 层数不超过货物堆码级别，尊重承载能力 |
| 5 | 均衡层高 | 不限（all） | 按可用件数反推层数、够用即止，竖直占位贴合实际货量 |

> **姿态档是「偏好」，不是硬约束。** 若货物的六向限制（`A~F_ALLOW` / 承托级别=0）
> 恰好把某策略首选档的两个方向都禁掉，会自动**回退**到次偏好档，而不是返回 0 放置。
>
> 典型场景（用户实测）：水泵2 `480×380×380` 与水泵3 `515×380×425` 都只放行 dir0/dir1，
> 而这两个方向恰为 heightRank1 —— 修复前策略 0/1/3 全部返回 **0%**，界面显示"装不下"，
> 但用户手工能装下（630+330）。修复后 6 个策略均有结果，策略 3 达 82%、策略 5 达 82.7%。
>
> 回退在每次放置时按**当前剩余空间**解析，因此装载后期若首选姿态放不下，会再退一档收尾，
> 顺带把原先被搁置的余量装上（实测 40HQ 三货物装载率 28.2% → 87.7%）。

> 部分策略在特定输入下会收敛为同一套逐箱坐标（姿态档相同 + 分块几何等价时属几何必然）。
> 用 `node scripts/strategy-compare.mjs` 可在 8 个差异化场景下持续监测策略区分度。

## 3D 可视化

- **逐箱渲染**（默认）：按 **(货物, 姿态)** 分组，每组一个 `InstancedMesh`，每箱独立拾取，点击显示单箱坐标与逐件序号
- **逐箱描边**（默认开）：每箱 12 条棱合并成一个 `LineSegments`（一次 draw call），分层切片用 `setDrawRange` 精确裁剪；超过 2 万箱自动退回批次外壳线框
- **整块渲染**：按聚合块渲染，便于快速查看整体轮廓
- **配色**：优先用货物主数据的「颜色」字段；未设置时回退到按货物 id 哈希的稳定区分色（保证不同货物一眼可分）
- 视图切换（俯视/正视/侧视/透视）、分层切片、柜体/轮廓线开关、PNG 导出
- 相机按柜体在当前视线下的真实投影范围自动拟合，长宽比极端的柜体不会裁切

> **为什么必须按 (货物, 姿态) 分组，而不是只按货物？**
> `InstancedMesh` 只有一个共用几何体，批内所有箱的尺寸必须一致。而同一种货物在一次计算里
> **可能同时以多个姿态摆放** —— 例如 500×400×300 的货物，dir4 占位 300×400×500、dir5 占位 400×300×500。
> 只按货物分组会用首箱的尺寸画整批，后者被 x/y 转置地画错（实测 45HQ 两货物场景策略 5 有 **67%** 的箱受影响，
> 策略 3 有 40%），视觉上货物变成"细长竖板"。
> 依赖的不变式「逐箱尺寸只依赖 (货物, 姿态)」由测试锁定。

> **箱体按真实尺寸渲染，不做收缩**。算法把货物紧贴摆放（实测相邻箱间距恒为 0），
> 所以渲染也必须紧贴；早期版本给每箱每侧缩 0.5%「制造间隙」以显示边界，
> 结果整柜看起来发虚、且会被误读成货物之间真的有间隙。现在边界由逐箱描边表达。

## 柜型尺寸基准

首次启动会写入 3 个**默认参考柜型**（ISO 668 数值）：

| 柜型 | 内长 × 内宽 × 内高 | 载重 |
|---|---|---|
| 20GP | 5898 × 2352 × 2393 | 21770 |
| 40GP | 12032 × 2352 × 2393 | 26800 |
| 40HQ | 13556 × 2352 × 2698 | 26800 |

> ⚠️ **这些只是默认值，程序不会自动校正你的柜型数据。**
> 现实中同一型号的集装箱尺寸差异很大（实测有 40HQ 就是 11900×2340×2680，而非 ISO 的 13556×2352×2698），
> 容积差异约 12%，会直接影响装载率与车辆利用率。**请在「柜型管理」里按实际柜型填写。**

## 已知限制

- **多货物混装**：调度采用「多起点 + 轮转 + 块大小/足迹上限 + 残余整洁优先 + 残余前瞻」。
  - **多起点 = 12 组候选配置**（2 种货物优先级 × 6 组块上限/足迹上限/残余整洁/残余前瞻），**按字典序择优**：
    ① 装入的**货物种类数**多者优（**硬约束**）② 装载率高者优
    - 硬约束的原因：只按装载率挑会选中"装载率高但把某个货物整个饿死"的方案 ——
      实测 40HQ 三货物装载率 90.3%→92.8% 但种类数 18/18→**13/18**。
      **一份把某个品项整个漏掉的装柜单即使装载率更高也是废单。**
    - 货物优先级：「单箱体积降序」多货物场景更优；「箱数降序」在"某货物需要一条干净长条"时更优
    - 块体积上限 0.5 / 0.75 / 不限：上限小则每块矮、别的货物易介入但整体被切碎；上限大则一次成整块
    - 块足迹上限 0 / 0.6 / 0.75：**0.6 是逐层码放策略（1/2）的最优值**（实测 948），
      0 是满舱主块策略（3）的最优值（实测 960）—— 两者不可兼得。
    - **残余整洁优先**：两种姿态的块体积常常精确相等（同批箱子换朝向），
      此时不看"谁先枚举到"，而看**谁留下的剩余空间更规整**
    - **残余前瞻**（跨货物、深度 2）：评分 = 块体积 + β × **残余还能装多少箱**。
      破解「一次装得多却把残余占死」的局部最优陷阱 ——
      例：900mm 条带里选 dir0（264 箱）还是 dir1（180 箱但留下 385mm 可再放 132 箱）
    - 单货物直接跑 1 次，不付 12 倍代价。实测双货物 6.2ms、四货物 ~24ms，UI 无感
  - **别压在别人头上码**（`SpaceBlock.baseBoxId` + `pickSpaceFor` 的 stackBias）：
    两种货物**并排**长，而不是在同一垛里逐层交错。逐层码放的策略（0/1/2）在混装时
    原本只有 78%/82% —— 两种货物 x 步长不同（480 vs 515），逐层交替会把可用宽度
    一层层削掉（11520→11330→11040→…）；同一货物自己连续码层则完全稳定。
    修复后 0/1/2 提升到 **93%/92%/92%**，单货物场景与策略 3 完全不受影响。
  - **块上限仅在「仍有货物一件未装」时生效**，全部参与后解除以最大化装载率。
  - 20ft 装 3 种货物且含大扁平件（如 1200×900×150）时，剩余空间不足以容纳全部 3 种（几何限制）。
- **方向限制可能"饿死"某个策略**：已修复 —— 姿态档现为有序偏好，首选档不可行时自动回退。
  剩余的策略收敛现象（如细长件场景下策略 1 与 2/4 产出相同坐标）属几何必然，非缺陷。
- 六向「最大堆放数」「可承重」字段已存档但算法未使用；型变公差同样仅存档。
- 柜型的角件尺寸已存档，**角件冲突检测尚未实现**（装柜时不检查货物与角件的空间冲突）。
- 逐件坐标在前端内存中计算（约 300KB / 千箱），万箱级需后端分页或按需展开。
- 立方货物（三轴等长）6 个姿态映射到同一网格，策略天然不可区分（几何决定）。
